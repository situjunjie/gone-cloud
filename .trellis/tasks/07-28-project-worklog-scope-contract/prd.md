# 项目工作项工时范围契约

## Goal

为工作项详情提供由服务端统一解析层级范围的工时分页与汇总契约，使前端可在“当前工作项”和“全部递归子项”之间切换，且分页、排序、筛选、权限过滤和汇总使用同一数据口径。

## Background

- 工时是独立实体；工作项上的 `estimatedHours`、`actualHours` 是只读的物化聚合字段，由工时写事务维护并冗余存储在工作项中。
- 现有工时管理功能已经提供 `/admin-api/project/worklog/page` 与 `/admin-api/project/worklog/summary`，本任务为两者补充同一范围请求契约。
- 前端不得逐个查询子项后自行合并，否则 `total`、排序、筛选与汇总会失真。
- `estimatedWorkload` 已废弃，不能继续出现在工作项创建、完整更新、字段更新请求或读取 DTO 中，也不能影响工作项数据。

## Requirements

### R1. 范围请求契约

- `POST /admin-api/project/worklog/page` 与 `POST /admin-api/project/worklog/summary` 的请求体新增可选字段：

  ```json
  {
    "workItemId": 1001,
    "workItemScope": "SELF"
  }
  ```

- `workItemId` 可省略，以兼容现有项目级查询。
- `workItemScope` 仅可在传入 `workItemId` 时传入；没有 `workItemId` 时传入范围必须被请求校验拒绝。
- `workItemScope` 仅允许 `SELF` 与 `DESCENDANTS`。
- 有 `workItemId` 而未传 `workItemScope` 时，默认 `SELF`。
- `SELF` 仅包含根工作项；`DESCENDANTS` 包含根工作项的全部递归后代，但不包含根工作项。

### R2. 统一查询口径

- 服务端先一次性、且具备循环保护地解析可访问工作项 ID 集合，再对工时应用现有筛选、排序、分页及汇总。
- 不能针对每个子项查询或在应用层逐项合并，避免 N+1 查询。
- `DESCENDANTS` 没有后代时，分页返回空 `list` 与 `total = 0`；汇总返回零工时与空 `groups`。
- 相同筛选条件下，`page.total`、页面记录和 `summary` 必须来自相同范围与权限后的集合。
- `summary` 保留并支持 `WORK_ITEM`、`OWNER`、`CATEGORY`、`SPRINT` 四种 `groupBy`。

### R3. 权限与安全

- 无权访问的后代工作项不得进入工时记录、`total`、分组或任何聚合数值。
- 脏的循环父子关系必须终止递归，且不能无限查询或无限递归。
- 保持 `/admin-api` 路径、`{ code, data, msg }` 响应封装与现有项目/工作项授权边界。

### R4. 工作项 DTO 与聚合

- 工作项读取 DTO（至少 `get`、`page`）返回只读 `estimatedHours`、`actualHours`。
- 工作项创建、完整更新、字段更新请求均不定义 `estimatedWorkload`、`estimatedHours`、`actualHours`。
- `ProjectWorkItemDO` 与 `proj_work_item` 冗余保存非空的 `estimatedHours`、`actualHours` 合计；前端读取工作项时直接使用这两个只读字段，不再为页面逐项/批量扫描工时明细。
- 工时创建、更新、删除必须在同一事务内原子维护对应类型的工作项合计：创建加值、更新按新旧小时数差额调整、删除减值。工时类型和工作项保持不可变。
- 全量 SQL 与增量迁移为现有未删除工时回填两个合计，迁移后存量和新增数据的工作项读取及工时汇总都能反映正确值。
- 带有范围、日期、类别、负责人或迭代等筛选的工时汇总仍以独立工时明细表聚合，不能使用未区分筛选条件的工作项冗余字段。
- 不为废弃字段保留隐式写入或兼容映射；传入 `estimatedWorkload` 不得影响持久化数据或读取值。

### R5. 文档与测试

- 提供更新后的 DTO、范围枚举、接口文档，供前端根据精确契约接入。
- 补充接口级测试，覆盖：
  1. `SELF` 仅返回根项数据；
  2. `DESCENDANTS` 覆盖任意层级后代且排除根项；
  3. 无后代、筛选、分页 `total`、汇总一致性；
  4. 权限过滤不泄露后代数据；
  5. 脏循环父子关系有界终止；
  6. `estimatedWorkload` 无法影响工作项，聚合字段只读。

## Acceptance Criteria

- [ ] 两个接口的请求 DTO 具有完全相同的范围字段、默认值和校验规则。
- [ ] 范围集合在数据库层或现有批量层级机制中一次解析，并且循环关系安全终止。
- [ ] 范围、权限和全部筛选在分页、总数、排序、分组和汇总前统一生效。
- [ ] 无后代与无权限后代的结果不泄露记录、总数、分组或数值。
- [ ] 工作项读取 DTO 从只读物化合计返回工时；所有工作项写请求移除废弃或只读工时字段。
- [ ] 创建、编辑、删除工时后，事务内维护的工作项合计与独立工时汇总均反映聚合变化，且现有数据在迁移后已回填。
- [ ] 新增/调整的接口测试通过，且受影响模块的既有测试不回归。
- [ ] 接口文档准确说明范围、默认值、非法组合和空结果行为。

## Out of Scope

- 前端页面或前端聚合逻辑改造。
- 新增第三种范围语义（例如“根项加后代”）。
- 改变工作日志实体、分类、归属、日期或既有 `groupBy` 枚举的业务语义。
- 为历史 `estimatedWorkload` 数据做迁移或补偿，除非现有持久化契约研究表明确有不可避免的兼容性风险。

## Confirmed Decisions

- 范围为 `SELF` / `DESCENDANTS`，后代范围不含根项。
- 省略 `workItemId` 保持项目级查询；此时不得传范围。
- 默认范围为 `SELF`。
- 接口使用服务端范围解析而非客户端多请求合并。
- API 前缀和标准响应不变。
- 当前权限模型是项目级而非单工作项 ACL。范围查询继续要求现有 `WORKLOG_QUERY`；递归解析必须在每一层约束同租户、请求项目和未删除工作项，以排除损坏的跨项目关系，且不得把 `WORK_ITEM_QUERY` 变成新的查询前置权限。
- `proj_work_item` 使用邻接表 `parent_work_item_id`，没有现成的闭包表或后代查询。实现使用一次递归 CTE，并以稳定的工作项 ID 集合和 `UNION` 去重防止脏循环无限递归。
- 工时明细继续是权威业务实体；`proj_work_item.estimated_hours`、`actual_hours` 是受 Service 事务维护的物化读取模型。创建、更新、删除分别加值、按差额调整、减值；写入使用原子 SQL 并在更新/删除时使用行锁防止并发请求使用陈旧差额。
- 工作项读取改为直接映射物化字段，移除现有批量 `proj_worklog` 聚合读取；范围/筛选工时汇总继续查询 `proj_worklog`，以保持筛选口径正确。
- 基线建表和新增增量迁移同时增加两列，并根据未删除工时回填。工作项逻辑删除时，随同工时逻辑删除，不再额外维护即将不可见工作项的计数。

## Technical Notes

- 本地运行时为 MySQL 8.0.33，支持递归 CTE；聚焦 Mapper 测试使用 H2 MySQL 模式，必须用真实测试验证语法与循环终止行为。
- 分页与汇总当前已经共享 `WorklogMapper.buildQueryWrapper`。范围实现必须把直接的 `workItemId = ?` 条件替换为同一个已解析 ID 集合，并在空后代时显式短路，不能依赖空 `IN` 的框架行为。
- 当前项目不存在“同项目内仅部分子项不可见”的数据模型。权限测试将覆盖项目级拒绝与损坏跨项目后代不进入范围；新增逐工作项 ACL 不在本任务范围内。
- 工作项冗余合计是性能读取模型，不用于有筛选条件的工时 summary；任何手工数据修复仍应以 `proj_worklog` 重算回填。
