# 项目成员角色权限管理

## Goal

为 `project` 模块建立租户内全局模板和项目级 RBAC，使项目在创建时继承角色权限快照，并使同一用户在不同项目拥有相互独立的角色与权限。

## Background

- 现有 `proj_project_member.role` 只能保存 `OWNER`、`ADMIN`、`MEMBER`、`VIEWER` 中的单个角色，无法支持成员多角色和项目级角色维护。
- `proj_project.owner_user_id` 继续表示唯一项目负责人，但负责人身份不再建模为 `OWNER` 角色。
- 当前环境没有需要保留的有效项目业务数据，因此无需兼容或迁移旧单角色数据。
- 当前阶段只支持私有项目，非成员不能读取或操作项目数据。

## Requirements

### R1. 租户与权限目录

- R1.1：全局角色模板是租户内全局数据，各租户独立维护并严格隔离。
- R1.2：项目权限点由系统固定定义，不允许租户或项目新增、修改编码或删除。
- R1.3：首版项目权限目录为 `PROJECT_QUERY`、`PROJECT_UPDATE`、`PROJECT_ARCHIVE`、`MEMBER_QUERY`、`WORK_ITEM_QUERY`、`WORK_ITEM_CREATE`、`WORK_ITEM_UPDATE`、`WORK_ITEM_DELETE`、`WORK_ITEM_FIELD_QUERY`、`WORK_ITEM_FIELD_MANAGE`。
- R1.4：系统权限与项目权限使用独立编码空间。系统权限沿用 `project:resource:action`，项目权限使用 R1.3 的枚举编码，接口显式映射两层权限。

### R2. 内置角色

- R2.1：租户全局模板和每个项目都必须存在管理员、参与人两个内置角色。
- R2.2：管理员、参与人的内置标识、编码和名称不可修改，角色不可删除。
- R2.3：管理员直接拥有当前及未来新增的全部项目权限，管理员权限不可配置。
- R2.4：参与人必须保留 `PROJECT_QUERY`、`WORK_ITEM_QUERY`，其他可分配业务权限可在全局模板或单个项目中调整。
- R2.5：参与人默认拥有 `PROJECT_QUERY`、`MEMBER_QUERY`、`WORK_ITEM_QUERY`、`WORK_ITEM_CREATE`、`WORK_ITEM_UPDATE`、`WORK_ITEM_FIELD_QUERY`。
- R2.6：参与人默认不拥有项目修改/归档、工作项删除、项目字段管理及成员角色治理能力。

### R3. 全局模板与项目快照

- R3.1：租户可在全局模板中创建、修改、删除自定义角色，并维护参与人及自定义角色的权限分配。
- R3.2：创建项目时复制当前租户的全部全局角色及角色权限，形成项目独立快照。
- R3.3：项目创建后可独立创建、修改、删除自定义角色并调整角色权限，不影响全局模板或其他项目。
- R3.4：全局模板变更只影响之后创建的项目，不自动同步既有项目；本期不提供同步或重置能力。
- R3.5：仍有关联成员的项目自定义角色禁止删除，不自动解除成员角色。

### R4. 项目创建、成员与负责人

- R4.1：项目由具备系统级项目创建权限的当前登录用户创建，创建动作不要求项目角色。
- R4.2：创建人自动成为项目成员，并分配管理员和参与人两个角色。
- R4.3：负责人不同于创建人时，负责人自动成为项目成员并分配管理员角色，不强制分配参与人角色。
- R4.4：新增普通成员未显式指定角色时默认分配参与人角色。
- R4.5：成员必须至少拥有一个项目角色；不允许通过角色更新留下零角色成员，清空权限应显式移除成员。
- R4.6：成员可拥有多个角色，有效权限取所有角色允许权限的并集，不支持显式拒绝或角色优先级。
- R4.7：同一用户在不同项目的成员、角色与权限关系相互独立。
- R4.8：当前负责人必须拥有管理员角色，不能被移出项目或移除管理员角色，需先转移负责人。
- R4.9：转移负责人时，新负责人自动成为成员并获得管理员角色；旧负责人保留原有角色，后续可单独调整。
- R4.10：创建人在不再担任负责人时，其角色可调整，也可被移出项目。

### R5. 治理权限

- R5.1：租户全局角色模板的查询和维护由专用系统权限控制，不依赖任何项目成员身份。
- R5.2：项目成员增删、成员角色调整、项目角色增删改、项目角色授权及负责人转移，仅允许内置管理员执行，并同时通过对应系统权限。
- R5.3：项目成员和角色治理能力不进入参与人或自定义角色的可分配项目权限目录。

### R6. 双层鉴权与私有边界

- R6.1：除项目创建和租户全局管理外，项目内操作必须同时通过系统权限和当前项目权限校验。
- R6.2：项目管理员拥有全部项目权限，但不能绕过系统权限。
- R6.3：系统超级管理员及其他系统角色不能绕过项目成员和项目角色校验。
- R6.4：项目创建和修改仅允许 `PRIVATE`，非成员即使拥有系统查询权限也不能读取项目或工作项。
- R6.5：项目分页列表按当前登录用户的成员关系过滤，只返回其已加入的项目。

### R7. Backend Deliverables

- R7.1：交付数据库结构和初始化数据、全局及项目级角色管理 API、成员多角色 API、项目创建继承、项目级鉴权及接口契约。
- R7.2：交付覆盖成功路径、权限边界、租户/项目隔离、内置角色约束和非法关联的后端测试。

## Acceptance Criteria

- [ ] AC1：两个租户可维护同编码全局角色且互不影响，新项目只继承当前租户模板。
- [ ] AC2：权限目录 API 只返回固定项目权限；角色授权提交未知编码或系统权限编码时被拒绝。
- [ ] AC3：管理员、参与人无法改名或删除；管理员权限无法修改且对全部项目权限恒为允许。
- [ ] AC4：参与人权限可以调整，但无法移除 `PROJECT_QUERY`、`WORK_ITEM_QUERY`，初始权限符合 R2.5。
- [ ] AC5：新项目获得全局模板完整快照；修改全局模板不影响既有项目，修改项目角色不影响模板或其他项目。
- [ ] AC6：删除仍被成员使用的项目自定义角色时返回明确业务错误，数据保持不变。
- [ ] AC7：创建人自动关联管理员和参与人；不同的负责人自动关联管理员，且不会产生重复成员记录。
- [ ] AC8：新增普通成员默认成为参与人；空角色集合或移除最后一个角色被拒绝。
- [ ] AC9：成员的多角色权限按并集合并，同一用户在两个项目可得到不同鉴权结果。
- [ ] AC10：当前负责人不能失去管理员角色或被移除；转移后新负责人获得管理员，旧负责人角色不被隐式修改。
- [ ] AC11：非内置管理员不能治理项目成员、角色或授权；内置管理员缺少对应系统权限时同样被拒绝。
- [ ] AC12：全局模板管理员无需加入项目即可凭系统权限管理本租户模板，无权限时被拒绝。
- [ ] AC13：仅有系统权限或仅有项目权限均不能执行项目内受控操作，两层同时满足才允许。
- [ ] AC14：`PUBLIC` 创建/修改请求被拒绝；非成员（包括系统超级管理员）不能读取私有项目。
- [ ] AC15：项目分页只返回当前用户作为成员的项目，不泄露其他私有项目基础信息。
- [ ] AC16：成员、角色和授权接口拒绝跨租户、跨项目的角色编号或成员编号组合。
- [ ] AC17：后端 API、SQL 和测试足以支持后续管理端页面直接对接。

## Out Of Scope

- 管理端前端页面及交互实现。
- 旧单角色成员数据迁移与兼容读取。
- 既有项目重新同步或重置为最新全局模板。
- 公开项目及非成员隐式只读访问。
