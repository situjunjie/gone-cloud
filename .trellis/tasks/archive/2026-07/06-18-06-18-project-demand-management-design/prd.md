# Project Work Item Management Product Design

## Goal

Design the first project-management capability for `yudao-module-project`: work item management. The feature should let product and engineering teams capture, assign, track, and close work items with a clear lifecycle, while leaving room for later iteration planning, themes, boards, reports, and task linkage.

## Context

- `yudao-module-project` already exists as an empty business module with `api` and `server` submodules.
- The module is intended to implement project-management functions.
- The user asked to reference Aliyun Yunxiao work-item management documentation.
- Competitor research is persisted in `research/competitor-yunxiao-demand-management.md`.
- Yunxiao positions work item management as a full lifecycle from creation to implementation, with Scrum/Kanban support, collaboration, visual tracking, work item relations, templates, automation, and analytics.

## Product Positioning

`工作项管理` is the first usable work-item surface in the project module. It is not yet a full agile suite. The first release should focus on the delivery lifecycle of a single work item and make it reliable enough to become the foundation for later planning and execution features.

Work items must be anchored to a minimal `Project` workspace from day one. The first release does not implement full project portfolio management, but it must provide enough project metadata and membership boundaries so that work-item responsibility, private visibility, and future iteration planning have a stable root.

Primary users:

- Product manager: creates and refines work items, sets priority, tracks progress.
- Project manager: assigns work items to assignees, filters backlog, checks overdue and blocked items.
- Developer or tester: receives assigned work items, updates status, records progress.
- Department stakeholder: follows work item state and comments without editing delivery fields.

## MVP Scope

### 1. Project Basics

Provide minimal project management before or together with work-item management.

Required project fields:

- project cover
- project name
- visibility:
  - public: all organization users can access
  - private: only project members can access
- project code
- project description
- owner
- status

Project status:

- active: project can create and update work items
- archived: project remains queryable, but new work items should not be created

Membership:

- A project has members independent from visibility.
- Public projects are viewable by organization users, but the member list still represents actual participants.
- Private projects are accessible only to members.
- The first role set should stay small:
  - owner
  - admin
  - member
  - viewer

Validation:

- project name is required and capped at a practical length such as 128 characters.
- project code is required, unique in the tenant, and capped at a practical length such as 64 characters.
- owner must be an enabled system user.
- private project access checks must use the project member table.
- archived projects cannot be used as the target for new work items.

### 2. Work Item List

Provide an admin/project workspace list page for work items.

Required capabilities:

- Search by work item number and title.
- Filter by category, status, priority, assignee, creator, project, iteration, planned finish date, and tags.
- Sort by priority, updated time, planned finish date, and created time.
- Show columns:
  - work item number
  - title
  - category
  - status
  - priority
  - assignee
  - project
  - iteration
  - planned finish date
  - estimated workload
  - updated time
- Support row selection so batch actions can be added later.
- Provide entry points:
  - create work item
  - open work item detail
  - quick assign assignee
  - quick status transition

### 3. Work Item Creation

Create work item from the list page through a modal or drawer.

Required fields:

- title
- description
- category
- priority
- project
- assignee

Optional fields:

- iteration
- participants
- CC users
- tags
- planned start date
- planned finish date
- estimated workload
- parent work item

Default behavior:

- category defaults to `REQUIREMENT`.
- priority defaults to medium.
- status defaults to pending.
- creator is the current user.
- work item number is generated by the system, for example `WI-000001`.

Validation:

- title is required and capped at a practical length such as 128 characters.
- assignee is required and must be an enabled system user.
- project is required, must exist, and must be active.
- planned finish date cannot be earlier than planned start date.
- estimated workload cannot be negative.
- category must be one of `REQUIREMENT`, `WORK_ITEM`, `TASK`, or `BUG`.
- parent work item cannot be itself and should belong to the same tenant.

### 4. Work Item Detail

The detail page should be split into a main content area and a structured field panel, following the interaction pattern observed in Yunxiao.

Main content:

- title
- rich or plain description in the first implementation
- comments placeholder or comment list if low-cost
- operation history

Field panel:

- status
- assignee
- priority
- category
- project
- iteration
- participants
- CC users
- tags
- planned start date
- planned finish date
- estimated workload
- parent work item
- created by
- created time
- updated time

### 5. Assignment

MVP supports manual assignment only.

Rules:

- Assignee can be set during creation.
- Assignee can be updated from list quick action or detail field panel.
- Assignee changes must be recorded in operation history.
- Future automation assignment should be modeled as a separate capability, not embedded into the MVP service logic.

### 6. Status Lifecycle

Use a simple lifecycle aligned with the competitor import template:

- pending: newly created or not started.
- designing: being clarified or designed.
- developing: implementation in progress.
- testing: validation in progress.
- completed: delivered and accepted.
- canceled: no longer planned.

Recommended transitions:

- pending -> designing, developing, canceled
- designing -> pending, developing, canceled
- developing -> designing, testing, canceled
- testing -> developing, completed, canceled
- completed -> testing only for reopen
- canceled -> pending only for restore

Every transition should record:

- previous status
- new status
- operator
- operation time
- optional reason or remark

### 7. Work Item Relations

MVP should include minimal relation support to avoid a later data-model break.

Required:

- parent-child relation for work item splitting.
- related-work-item relation for loose association.

Out of MVP:

- relation to code changes, releases, and pipelines. Tasks and defects are represented by work items with category `TASK` and `BUG`.

### 8. Operation History

Record history for important changes:

- create work item
- update title or description
- update assignee
- update priority
- update status
- update planned dates
- update estimated workload
- add or remove participant
- add or remove tag
- add or remove relation
- cancel or restore

History should be queryable from the work item detail page.

## Data Concepts

Suggested entities:

- `Project`: minimal project workspace and metadata.
- `ProjectMember`: project membership and project-level role.
- `ProjectWorkItem`: main aggregate.
- `ProjectWorkItemParticipant`: participant and CC membership.
- `ProjectWorkItemTag`: work item tags.
- `ProjectWorkItemRelation`: parent-child and related-work-item links.
- `ProjectWorkItemHistory`: operation and field-change history.

Suggested dictionaries:

- `project_visibility`: public, private.
- `project_status`: active, archived.
- `project_member_role`: owner, admin, member, viewer.
- `project_work_item_category`: requirement, generic work item, task, bug.
- `project_work_item_priority`: urgent, high, medium, low.
- `project_work_item_status`: pending, designing, developing, testing, completed, canceled.
- `project_work_item_relation_type`: parent_child, related.

Admin/project management APIs:

- `POST /project/project/create`
- `PUT /project/project/update`
- `GET /project/project/get`
- `GET /project/project/page`
- `PUT /project/project/archive`
- `POST /project/project/member/add`
- `PUT /project/project/member/update-role`
- `DELETE /project/project/member/remove`
- `GET /project/project/member-list`
- `POST /project/work-item/create`
- `PUT /project/work-item/update`
- `DELETE /project/work-item/delete`
- `GET /project/work-item/get`
- `GET /project/work-item/page`
- `PUT /project/work-item/assign`
- `PUT /project/work-item/transition-status`
- `POST /project/work-item/relation/create`
- `DELETE /project/work-item/relation/delete`
- `GET /project/work-item/history-list`

The exact controller package should follow existing Yudao admin conventions under `cn.iocoder.yudao.module.project.controller.admin`.

## Out Of Scope For MVP

- Frontend implementation unless requested separately.
- Excel import and import task result management.
- Custom work-item template management.
- Automation rules.
- Product theme management and value/workload scoring.
- Scrum board, Kanban board, burn-down charts, and dashboards.
- Full project workspace management beyond basic metadata, membership, visibility, and archive state.
- Full iteration/sprint management.
- Task execution integration.
- Notification delivery.
- Complex field-level permission matrix.

## Future Roadmap

Phase 2:

- Work Item import with `.xlsx` template download, validation, result tracking, and failed-row export.
- Saved list views.
- Comment and mention notification.
- Basic Kanban board by status.

Phase 3:

- Product themes that group work items across projects and rank by value/workload.
- Iteration planning and burn-down chart.
- Work-item template management and custom fields.
- Automation rules for assignment and state transitions.

Phase 4:

- Link work items to tasks, defects, code branches, releases, and DevOps changes.
- Analytics dashboard for lead time, throughput, overdue rate, and status distribution.

## Open Questions

- Is there already a frontend route namespace reserved for project management?
- Should tags be free text for the first implementation, or should we introduce a reusable project tag table immediately?
- Should description be rich text storage from day one, or plain text/Markdown first?
- Should delete be physical delete, soft delete through existing base fields, or status cancellation only?
