# 工作项字段变更动态评估与设计

## Goal

为项目工作项提供可查询的字段修改动态，记录每次字段更新的操作者、时间、字段及变更前后值；优先复用系统现有 `@LogRecord` 框架，避免另建一套重复的操作日志机制。

评估与设计已经确认，当前任务已完成后端实现和质量验证。

## Background

- 系统使用 `bizlog-sdk 3.0.6`，并在 System、CRM、DevOps 等模块使用 `@LogRecord`。
- 项目适配层将日志异步写入统一 `system_operate_log`；mzt 服务自身的查询方法被禁用，跨模块查询通过 system `OperateLogApi` 完成。
- 工作项已有 `PUT /project/work-item/update-field`，支持固定字段与 `custom:<fieldId>` 混合批量局部更新，所有写入位于同一业务事务。
- 固定字段会在写入前剔除未变化值；自定义字段采用类型化存储和局部物理替换，需要通过前后规范化快照判断真实变化。
- system 日志查询已支持 `type + bizId` 精确分页，能够以工作项主键 ID 作为 `bizId` 查询。

## Requirements

- 评估现有 `@LogRecord` 的表达能力、持久化模型、事务时机、查询能力和扩展成本，明确能否满足工作项字段变更动态。
- 梳理工作项单字段更新接口覆盖的系统字段、自定义字段及特殊更新路径，确定日志接入边界。
- 若可复用，设计基于工作项字段更新接口的记录方案，包括 `type`、`subType`、`bizNo`、内容模板、旧值/新值获取和字段值可读化。
- 设计按工作项主键 ID 查询变动记录的后端接口、权限边界、排序与分页策略。
- 识别对现有模块共用 `@LogRecord` 基础设施的兼容性影响，不破坏既有日志写入与查询行为。
- 给出测试、迁移、发布、回滚及异常降级方案。
- 将必须由产品或技术负责人确认的决策集中列出，供用户一次性确认。

## Constraints

- 现有日志写入是异步、最终一致，默认不与业务事务强绑定；活动动态允许该模式时才可直接复用。
- `system_operate_log.action` 与 `extra` 的 MySQL 列长度均为 2000 字符，不能作为任意长度字段值的完整审计存储。
- 当前动态请求结构不适合直接使用 mzt `_DIFF`，必须由 project 模块生成工作项专用变更摘要或结构化变更列表。
- 查询接口必须先校验工作项 `WORK_ITEM_QUERY` 权限，再使用固定日志 type 和工作项 ID 查询，不能暴露通用操作日志检索能力。

## Acceptance Criteria

- [x] 有代码证据支撑的 `@LogRecord` 适用性结论，包含能力满足项、缺口、风险与推荐方案。
- [x] 明确工作项更新链路中所有应记录与暂不记录的入口。
- [x] 形成可实施的 `design.md`，覆盖数据流、接口契约、持久化/查询、权限、事务、兼容和性能。
- [x] 形成可执行的 `implement.md`，包含改动步骤、验证命令、测试范围和回滚点。
- [x] 完成完整更新、快捷更新、结构化变更记录和按工作项主键分页查询的后端实现。
- [x] 未决事项只保留仓库证据无法回答的产品/风险决策，并集中交由用户确认。

## Decisions

- 同时覆盖 `update-field` 和现有完整 `update`，避免修改历史不完整。
- 一次请求记录一条动态，记录内包含本次请求的多个实际字段变化。
- 定位为面向展示的活动动态：保存可读值，超长文本按统一策略截断，复用 `system_operate_log`。
- 接受现有异步最终一致和短暂查询延迟，不在本任务引入专用表/outbox。
- 不补录上线前历史。
- 不直接使用 `_DIFF{#updateReqVO}`；由 project 模块的工作项专用比较器生成 `changed`、`summary` 和结构化 `extra`，再通过 `LogRecordContext` 提供给 `@LogRecord` 模板。

## Out Of Scope

- 不实现前端页面。
- 不重构其他模块已有的 `@LogRecord` 用法，除非评估证明共享基础设施存在必须同步修复的问题。
- 不默认补录功能上线前的工作项历史变动。
