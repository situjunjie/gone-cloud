# DevOps Pattern Research

Date checked: 2026-06-03

## Scope

研究与“应用 / 环境 / 变更 / 部署流程”相关的行业模式，重点对比：

- 阿里云云效高级版变更持续交付
- GitLab environments / deployments / approvals

## Source Notes

### 1. 云效 AppStack / 变更持续交付

阿里云官方文档显示，一个完整应用生命周期按如下步骤组织：

- 代码源设置
- 部署编排
- 环境规划
- 研发流程配置
- 应用发布

并且官方明确写到“应用发布：新建变更，运行研发流程，完成一次完整的应用交付”。

来源：

- 阿里云《应用全生命周期管理指南》  
  https://help.aliyun.com/zh/yunxiao/user-guide/application-management-1

关键信息：

- 一个应用最多关联 1 个代码仓库。
- 应用下配置环境。
- 研发流程按测试、预发、生产等阶段配置，支持准入规则和人工卡点。
- 变更列表展示变更名称、分支、负责人、状态。
- 变更详情展示分支、最新提交 commit、关联工作项、流程元数据。

来源：

- 阿里云《如何将云效流水线模式变更为持续交付模式》  
  https://help.aliyun.com/zh/yunxiao/user-guide/change-the-continuous-delivery-model

### 2. GitLab Environments / Deployments

GitLab 官方文档体现的是“环境 / 部署中心”模型：

- Environment 是明确的部署目标，如 development、staging、production。
- Deployment 是某次代码版本部署到某个环境的记录。
- 一个环境通常同一时刻只有一个 active deployment。
- 系统追踪每个环境的部署历史、回滚、审批和保护。

来源：

- GitLab Environments  
  https://docs.gitlab.com/ci/environments/
- GitLab Deployments  
  https://docs.gitlab.com/ci/environments/deployments/
- GitLab Deploy & Release Getting Started  
  https://docs.gitlab.com/user/get_started/get_started_deploy_release/

关键信息：

- GitLab 支持静态环境和动态环境。
- 可以限制敏感变量只在特定环境可用。
- 支持 protected environments、manual deployments、deployment approvals。
- 回滚在模型上仍然是一条新的 deployment 记录，指向旧 commit。

## Pattern Extraction

### 模式 1：应用作为长期配置容器

云效表明，应用不是一次发布，而是长期存在的配置容器，承载：

- 唯一代码源
- 编排定义
- 环境规划
- 研发流程配置

这与用户提出的“应用关联唯一代码库、多个环境、每个环境有部署流程”高度一致。

### 模式 2：环境是长期目标，变更/部署是流经环境的短期对象

GitLab 和云效都体现出同一事实：

- 环境本身是长期对象
- 每次交付会产生新的执行记录
- 系统必须回答“某环境当前是什么版本”

所以环境应当建模为稳定资源边界，而不是一次性流水线节点。

### 模式 3：变更应当比部署记录更高一层

从云效的表述看，变更不仅是一次部署：

- 它有负责人
- 它绑定分支和提交
- 它能关联工作项
- 它有贯穿研发流程各阶段的元数据

这说明“变更”更像是研发生命周期的业务对象，而“部署”只是变更在某环境上的一个动作或结果。

### 模式 4：审批 / 准入 / 卡点应该挂在环境推进上

GitLab 和云效都支持：

- 手动触发
- 环境保护
- 审批规则
- 阶段卡点

因此更合理的模型不是“流水线成功即自动一路到底”，而是：

- 变更与多个环境发生关系
- 某环境是否接纳某变更，需要独立记录和治理
- 环境级别支持人工批准和回滚

### 模式 5：环境流水线是环境自己的执行器

从 GitLab 和云效的通用模式可以抽象出一点：

- 环境不是纯标签
- 环境承载自己的执行规则、审批策略、变量和发布动作

映射到本项目，更合理的建模是“每个环境有自己的流水线”，而不是“应用只有一条全局流水线对所有环境一视同仁”。

## Mapping to This Product

对本项目的推荐建模如下：

### 一级对象

- `应用`：DevOps 配置和交付容器
- `环境`：应用下的长期部署目标
- `变更`：研发生命周期主对象，绑定分支

### 二级对象

- `部署流程模板`：某环境采用的部署流程定义
- `变更环境实例`：某变更在某环境中的落点、审批、部署、包含关系状态
- `环境运行快照`：某环境某次运行时的变更集合与代码基线快照
- `部署记录`：某次真实执行的构建/部署结果
- `制品版本`：归属于环境运行快照的可部署产物
- `环境流水线执行记录`：环境一次完整执行的运行结果

### 建议关系

- 一个应用 -> 一个代码库
- 一个应用 -> 一个全局主干分支（当前为 `master`）
- 一个应用 -> 多个环境
- 一个环境 -> 一个主部署流程模板
- 一个应用 -> 多个变更
- 一个变更 -> 一个分支
- 一个变更 -> 多个环境实例
- 一个环境推进实例 -> 多次部署记录

## Design Implication

### 推荐 MVP 结论

MVP 先采用：

- `单应用`
- `单代码库`
- `变更绑定单分支`
- `变更可以同时存在于多个环境`
- `变更状态` 与 `环境状态` 解耦
- `环境部署分支` 为部署时派生的临时结果分支，而不是长期主干

不要在第一阶段就支持：

- 一个变更跨多个应用
- 一个变更跨多个代码库
- 面向大规模微服务集群的一次性发布编排

### Why

- 更容易把状态机做清楚。
- 更容易把页面结构做稳定。
- 更容易把审计、审批、回滚做扎实。
- 后续可以在此之上抽象“变更集 / 发布单”来覆盖跨应用场景。
