# Project 评论模块初版设计

## Goal

在 `project` 模块内提供可复用的协作评论能力，让项目成员围绕工作项持续讨论、回复和 @ 相关成员，同时遵守现有租户隔离、私有项目成员边界以及项目角色权限模型。

首期以工作项详情页为唯一接入场景，但评论能力的业务边界不与工作项表结构硬绑定，为后续接入项目、迭代等项目内对象保留明确扩展点。

## Background

- 当前 `yudao-module-project` 已实现项目、成员、项目角色权限和工作项，但没有评论包、评论表或评论接口。
- 归档的需求管理设计已将“评论与 @ 提醒通知”列为工作项后续能力；首轮工作项实现明确未包含评论。
- 项目数据只对私有项目成员开放；系统超级管理员若不是项目成员，也不能绕过项目权限。
- 现有商城商品评论是评分、晒单和商家回复模型，不适合复用为项目协作评论。
- 系统模块已有 Admin 用户查询与单用户站内信发送 API；infra 模块已有文件上传能力，但其文件内容下载接口当前允许匿名访问。

## Users And Value

- 产品经理、项目经理：在工作项下补充背景、澄清范围并 @ 负责人。
- 开发、测试：回复问题、同步处理结论，不必把过程信息混入工作项描述。
- 项目干系人：在具有评论权限时查看讨论或参与讨论，无需获得工作项字段修改权限。

## Requirements

### R1. Target Boundary

- 评论必须属于一个租户和一个私有项目。
- 评论目标使用固定、服务端可识别的目标类型；首期只支持 `WORK_ITEM`。
- 创建或查询评论时，服务端必须从目标记录解析真实 `projectId`，不得信任客户端单独提交的项目编号。
- 目标不存在、已逻辑删除或跨租户时，表现为目标不存在。
- 后续增加目标类型时，必须新增显式解析和授权规则，不能接受任意字符串表名或任意对象编号。

### R2. Comment Lifecycle

- 有权限的项目成员可以创建非空评论。
- 评论正文首期最多 10,000 个字符；仅空白字符不算有效正文。
- 评论可以引用同一目标下的一条已有评论作为回复对象；不允许跨目标回复。
- 评论作者可以编辑自己的正常评论，作者身份和目标不可修改。
- 评论作者可以删除自己的评论；项目管理员可以删除项目内任意评论。
- 已删除评论保留占位和作者、时间等基础审计信息，不再返回原正文和 @ 关系，保证回复引用仍可解释。
- 已删除评论不能再次编辑、删除或作为新回复的引用目标。
- 项目归档后允许读取历史评论，但禁止新增、编辑和删除。

### R3. Timeline Query

- 客户端可以按目标分页读取评论，默认按创建时间和编号稳定排序。
- 响应包含评论编号、目标类型与编号、作者用户信息、正文、回复对象摘要、编辑状态、删除状态、创建时间和更新时间。
- 用户昵称和头像以当前系统用户资料为准；用户停用或资料变更不影响历史评论归属。
- 评论查询不得出现逐条查询作者或回复对象的 N+1 调用。
- 首期不在工作项主表维护冗余评论数；需要数量时由评论查询能力计算。

### R4. Mentions

- 创建或编辑评论时，客户端显式提交 `mentionUserIds`；服务端不得通过扫描正文中的 `@昵称` 推断接收人。
- 被 @ 用户必须是当前项目成员，重复用户需去重，评论作者本人不发送提醒。
- 单条评论最多 @ 20 人。
- 编辑评论只对本次新增的 @ 用户发送提醒，避免重复通知已有接收人。
- 评论写入成功后再发送站内信；通知失败不得回滚评论，但必须记录可定位的失败日志。
- 通知只包含必要摘要和目标定位信息，不记录完整长正文。

### R5. Authorization

- 评论已位于具体项目工作项内，所有接口只校验项目角色权限，不增加系统菜单权限。
- 新增项目权限能力：`COMMENT_QUERY`、`COMMENT_CREATE`、`COMMENT_UPDATE`、`COMMENT_DELETE`。
- 内置 `ADMIN` 自动拥有全部评论权限；内置 `PARTICIPANT` 默认拥有四项评论权限。
- 查询、创建按目标解析所属项目后授权；更新、删除按评论记录解析所属项目后授权。
- `COMMENT_UPDATE` 只允许作者编辑自己的评论；`COMMENT_DELETE` 允许作者删除自己的评论，项目管理员可以删除任意评论。
- 评论权限不隐含工作项字段更新权限，评论参与者无需获得 `WORK_ITEM_UPDATE`。

### R6. Tenant, Security And Audit

- 评论与 @ 关系必须受 `tenant_id` 隔离并使用项目模块既有审计字段。
- 正文采用 Markdown 源文本并按不可信文本处理；首期不接受原始 HTML，展示端必须禁用原始 HTML并对渲染结果做 XSS 清理。
- 删除操作不得依赖直接逻辑删除根记录，以免回复引用失效。
- 服务端日志不得记录完整评论正文或附件内容。

### R7. API And Frontend Contract

- 管理后台提供创建、更新、删除、分页查询四类接口，统一返回 `CommonResult` / `PageResult`。
- 请求和响应 VO 需要 OpenAPI 字段说明与 Bean Validation。
- 交付时补充 comment 前端接口文档，说明权限、分页顺序、删除占位、回复引用和 @ 用户协议。

## Acceptance Criteria

- [x] AC1: `WORK_ITEM` 目标可创建、分页查询、编辑和删除评论，非法目标类型及不存在目标被拒绝。（R1、R2、R3）
- [x] AC2: 评论回复只能引用同一目标的正常评论，跨目标或已删除引用被拒绝。（R2）
- [x] AC3: 删除后正文和 @ 关系不可读取，但引用该评论的历史记录仍能显示删除占位。（R2、R3、R6）
- [x] AC4: 作者、普通成员、项目管理员分别满足所有权与管理权限规则，缺少对应项目评论权限时返回拒绝，且不依赖系统菜单权限。（R5）
- [x] AC5: 非项目成员、跨租户请求及伪造目标/项目归属不能读取或修改评论。（R1、R5、R6）
- [x] AC6: @ 用户仅允许当前项目成员，自动去重且最多 20 人；编辑仅提醒新增 @ 用户。（R4）
- [x] AC7: 评论事务提交后触发站内信；通知异常不会回滚评论，并留下不含完整正文的结构化日志。（R4、R6）
- [x] AC8: 分页顺序在相同创建时间下仍稳定，作者与回复摘要批量装配，无逐条 RPC/SQL 查询。（R3）
- [x] AC9: 归档项目评论可读不可写；删除和编辑已删除评论均失败。（R2）
- [ ] AC10: comment 相关 Controller、Service、Mapper 与方法安全测试覆盖正常、边界和拒绝路径，project server 模块测试通过。（R1-R7）
- [x] AC11: 前端接口文档与实际 Controller/VO 契约一致。（R7）

AC10 说明：35 个本任务聚焦测试已全部通过；全量模块测试剩余失败均来自外部增量编译器覆盖既有 MapStruct 生成类，不涉及 comment 包或本任务新增行为。

## Out Of Scope For V1

- 附件上传与附件级访问控制。
- 图片粘贴、富文本 HTML、表情反应、点赞和投票。
- 多级嵌套讨论树、评论置顶、解决/未解决状态。
- 评论全文检索、导出、合规留存和管理员恢复正文。
- 邮件、短信、WebSocket 实时推送以及用户级通知偏好。
- 项目、迭代等 `WORK_ITEM` 之外目标类型的实际接口开放。
- 前端页面实现；本任务默认交付后端和前端对接文档。
