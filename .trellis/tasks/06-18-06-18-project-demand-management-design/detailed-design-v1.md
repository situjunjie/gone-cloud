# Project Work Item Management V1 Detailed Design

## 1. Objective

Build the first usable work-item management release for `yudao-module-project`.

The release should let a team:

- create a work item
- view and filter the work item list
- open work item detail
- edit core fields
- assign an assignee
- change status with validation
- record operation history
- keep parent/related work item links

This version is intentionally smaller than Yunxiao’s full project collaboration suite. It covers the delivery lifecycle first and keeps room for future import, theme planning, automation, and board views.

## 2. Product Boundary

### In Scope

- Minimal Project workspace metadata
- Project visibility and membership boundary
- Project archive state
- Work Item list
- Work Item create/update/detail
- Assignee assignment
- Status transition
- Parent-child work item relation
- Related-work-item relation
- Operation history
- Basic filters and sorting

### Out of Scope

- Excel import
- Work Item template builder
- Automation rules
- Product theme management
- Kanban/Scrum board
- Burn-down chart
- Analytics dashboard
- Full project portfolio management beyond basic metadata, membership, visibility, and archive state
- Release/code-change/pipeline integration. Tasks and defects are modeled as work items with `category=TASK` and `category=BUG`.

## 3. User Roles

- Product manager: creates and prioritizes work items.
- Project manager: assigns work items to assignees and checks overdue work.
- Developer/tester: updates status and execution notes.
- Stakeholder: views progress and comments.

## 5. Domain Model

### 5.1 Aggregates

Primary aggregate: `Project`

Responsibility:

- own the project metadata
- own visibility and archive state
- serve as the access boundary for private projects
- serve as the root for project members and work items

Primary aggregate: `Work Item`

Responsibility:

- own the work item lifecycle
- own the current business fields
- own the status machine
- serve as the root of relations and history

## 7. State Machine

### 7.1 Default State

- new work item starts in `pending`

### 7.2 Allowed Transitions

- `pending` -> `designing`, `developing`, `canceled`
- `designing` -> `pending`, `developing`, `canceled`
- `developing` -> `designing`, `testing`, `canceled`
- `testing` -> `developing`, `completed`, `canceled`
- `completed` -> `testing`
- `canceled` -> `pending`

### 7.3 Transition Rules

- transition must be validated server-side
- invalid transition returns a business error
- every transition writes history
- transition can optionally carry a reason/remark

### 7.4 Notes

This V1 keeps the state machine simple and explicit. If later workflow automation is added, it should call the same transition service rather than bypass it.

## 9. Validation Rules

Project:

- project name is required
- project name max length: 128
- project code is required
- project code max length: 64
- project code must be unique in the tenant
- visibility must be one of `PUBLIC` or `PRIVATE`
- owner must be an enabled system user
- project must keep exactly one owner member
- owner cannot be removed before ownership transfer
- archived project cannot be used for new work item creation
- private project access must be checked by membership

Work item:

- title is required
- title max length: 128
- description max length: 2000 or 5000 depending on UI storage choice
- category required
- category must be one of `REQUIREMENT`, `WORK_ITEM`, `TASK`, or `BUG`
- priority required
- assignee is required
- assignee must be an enabled system user
- project is required in V1
- project must exist in the same tenant
- project must be active when creating a work item
- planned end time must be after planned start time
- estimated workload must be non-negative
- parent work item cannot equal current work item
- parent work item must be same tenant
- relation target cannot equal source work item
- duplicate relation rows must be rejected or merged

## 10. Persistence Design

### 10.1 Table Name Proposal

- `proj_project`
- `proj_project_member`
- `proj_work_item`
- `proj_work_item_relation`
- `proj_work_item_participant`
- `proj_work_item_tag`
- `proj_work_item_history`

### 10.2 Index Proposal

For `proj_project`:

- unique `(tenant_id, code)`
- index `(tenant_id, visibility)`
- index `(tenant_id, status)`
- index `(tenant_id, owner_user_id)`

For `proj_project_member`:

- unique `(tenant_id, project_id, user_id)`
- index `(tenant_id, user_id)`
- index `(tenant_id, project_id, role)`

For `proj_work_item`:

- unique `(tenant_id, work_item_no)`
- index `(tenant_id, status)`
- index `(tenant_id, assignee_user_id)`
- index `(tenant_id, project_id)`
- index `(tenant_id, iteration_id)`
- index `(tenant_id, parent_work_item_id)`
- index `(tenant_id, planned_end_time)`

For relation/history tables:

- relation unique key on `(tenant_id, work_item_id, related_work_item_id, relation_type)`
- history index on `(tenant_id, work_item_id, operation_time)`

### 10.3 Soft Delete

Use the repository standard logical-delete pattern.

### 10.4 Tenant Scope

All project and work item data is tenant-scoped.

### 11.3 Service Responsibilities

- validate project metadata and owner
- coordinate project and owner member writes
- enforce project archive behavior
- provide access checks for private projects

Work item service:

- validate business rules
- validate project existence and active state
- coordinate main table and relation/history writes
- enforce status machine
- write operation history
- preserve consistency in transactions

### 11.4 Transaction Boundaries

Use `@Transactional(rollbackFor = Exception.class)` for:

- project create with owner member write
- project owner transfer
- project archive
- member add/update/remove
- create with relation/history writes
- update with participant/tag/relation replacement
- status transitions
- delete with cascading logical cleanup

## 18. Acceptance Criteria

- Project basics can be created, updated, paged, fetched, and archived.
- Private project access is backed by project membership.
- Project owner is always present as a project member.
- Work Items must belong to an active project.
- Work Item CRUD fits the existing Yudao admin style.
- Work Item list and detail can be implemented from this contract.
- Status changes are validated centrally.
- History records are persisted.
- The design leaves room for import, themes, and automation later.

## 19. Notes From Yunxiao Reference

Yunxiao’s docs suggest three layers worth preserving in future work:

- raw work item intake
- theme aggregation for prioritization
- work item delivery tracking

V1 should only implement the third layer, while keeping the data model open enough to add the first two later.
